# Процесс подготовки выпуска

## Статус процедуры

Цель `make release-candidate RELEASE_COMMIT=<40hex>` создаёт локальный кандидат
только из указанного неизменяемого commit. Кандидат нельзя собирать вручную из
рабочего дерева и называть официальным.

Builder требует, чтобы `HEAD` точно совпадал с `RELEASE_COMMIT`, а checkout не
содержал отслеживаемых или неотслеживаемых изменений. Фактически выполняемый
builder побайтно сверяется с его копией в release commit. Зависимости
загружаются и проверяются в отдельных npm/Go caches каждого чистого снимка;
окружение Python изолируется.

Результат цели является только локальным кандидатом для финального ревью Task
11. До решения `РАЗРЕШИТЬ ВЫПУСК` его запрещено публиковать. Эта процедура не
создаёт tag, не выполняет `push`, не создаёт GitHub Release и не выполняет
deployment или mainnet-транзакции.

## Модель репозиториев

`origin` используется как рабочий fork. `upstream` используется только как
источник для `fetch` и контролируемой синхронизации. Скрипты репозитория не
изменяют remotes и никогда не выполняют `push`, создание tag или публикацию
выпуска.

Оператору рекомендуется запретить случайный push в `upstream` локальной
настройкой:

```sh
git remote set-url --push upstream DISABLED
git remote -v
```

Эти команды выполняет и проверяет оператор. Агент их не выполняет. В публичное
доказательство не включаются реальные URL `origin` или `upstream`.

## Предварительные условия

Кандидат строится только после выполнения всех условий:

- Tasks 01-10 имеют статус `DONE`, а отчёты их независимого ревью проверены;
- в отчётах и реестре нет открытых findings уровня Critical или High;
- полный CI прошёл для выбранного commit;
- оператор предоставил редактированное доказательство required checks,
  branch rules и Dependabot по правилам [evidence/README.md](evidence/README.md);
- выбранный release commit уже существует как неизменяемый Git commit;
- release commit задан полным 40-символьным SHA-1 в нижнем регистре, а не
  именем ветки, tag, сокращённым SHA или значением `HEAD`;
- в commit входят lock-файлы, контрактный артефакт, схема manifest,
  русскоязычные runbooks и отчёты ревью Tasks 01-10.

Подготовительные проверки:

```sh
npm ci
make security-validation
make documentation-check
make operations-check
make operations-rehearsal
```

`operations-rehearsal` не использует production RPC или production secrets.
Deployment-тест подписывает локальным тестовым ключом и отправляет транзакцию
только в одноразовый Anvil; production activation command и публичная сеть не
используются.

## Выбор коммита

Оператор фиксирует полный идентификатор уже проверенного commit и убеждается,
что это commit object:

```sh
git rev-parse --verify '<40hex>^{commit}'
git show --no-patch --format='%H' '<40hex>'
```

Обе команды должны вывести один и тот же `<40hex>`. Значение передаётся явно:

```sh
make release-candidate RELEASE_COMMIT=<40hex>
```

Цель отклоняет отсутствующий или неканонический идентификатор, несовпадение
`HEAD` и любое изменение checkout. Она читает snapshot непосредственно из
указанного commit и не подмешивает содержимое рабочего дерева. Наличие
локального объекта обязательно; Git ничего не загружает из сети.

## Детерминированная сборка

Цель вызывает собственный Python-генератор репозитория и создаёт
ровно один каталог:

```text
dist/release/<commit>/
```

`dist/` игнорируется Git. Генератор не получает секрет подписи и не выполняет
EVM-вызовы или deployment. `npm ci` и Go могут обращаться только к обычным
реестрам закреплённых зависимостей. Двоичный файл собирается для `linux/amd64` с
`CGO_ENABLED=0`, `-trimpath`, отключённой VCS-меткой и пустым Go build ID.
Исходный tar является точным выводом `git archive --format=tar` с фиксированным
префиксом `guard-daemon-<commit>/`: его нельзя перепаковывать, дополнять или
сжимать после создания.

Метаданные сериализуются канонически с устойчивым порядком ключей и массивов.
В них не включаются время сборки, имя узла, имя пользователя, текущий каталог
или значения окружения. SBOM имеет формат CycloneDX 1.6 JSON. Документ
происхождения имеет формат одной неподписанной in-toto Statement с SLSA
Provenance v1, записанной как JSONL. Полный состав описан в
[artifacts.md](artifacts.md).

SBOM строится из `package-lock.json`, списка модулей и `go mod graph`, поэтому
сохраняет прямые и транзитивные связи Go, включая закреплённые replacements.
Provenance фиксирует SHA-256 фактически выполненного builder из source archive.

## Проверка кандидата

После сборки выполняются пункты [checklist.md](checklist.md). Обязательны две
чистые независимые сборки одного commit, побайтовое совпадение файлов, проверка
`SHA256SUMS`, проверка схем JSON и поиск секретов во всём созданном каталоге.

Расхождение хотя бы одного байта блокирует кандидат. Исправление выполняется в
новом commit, после чего выбирается новый `<40hex>` и все проверки повторяются.
Содержимое уже проверенного каталога не исправляется вручную.

## Манифест развёртывания

Кандидат содержит только `rescuer-manifest.schema.json`. Официальный deployment
manifest с release commit создаётся оператором или отдельным keyless CI только
после существования проверенного кандидата. Manifest нельзя создавать заранее,
подменять им release metadata или добавлять в кандидат задним числом.

Создание manifest не означает разрешение активации mainnet. Chain, destination,
sponsor, runtime identity, ограниченное пополнение и чтение состояния после
развёртывания проверяются отдельно по runbook развёртывания. Агент не выполняет
эти действия.

## Подпись и публикация

Текущие GitHub Actions имеют только `contents: read`, не запрашивают OIDC token
и ничего не подписывают. Неподписанный provenance фиксирует заявленные входы и
результаты, но не подтверждает личность сборщика.

Подписывать артефакты разрешено только одним из способов:

- в отдельном keyless CI после проверки точной OIDC identity policy;
- оператором вне агента и вне среды репозитория.

Закрытый ключ и секрет подписи либо OIDC token нельзя передавать агенту,
сохранять в репозитории или добавлять в метаданные выпуска. `SHA256SUMS`
выявляет изменение файлов, но не аутентифицирует издателя и не заменяет подпись.

После локальной подготовки кандидат остаётся непубликуемым входом Task 11.
Только независимое решение Task 11 `РАЗРЕШИТЬ ВЫПУСК` позволяет оператору
начать отдельную процедуру подписи и публикации. Даже после этого tag, `push`,
GitHub Release и mainnet activation требуют отдельных явных операторских
действий и не выполняются release-скриптами.
