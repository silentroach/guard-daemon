# Процесс подготовки выпуска

## Статус процедуры

Цель `make release-candidate RELEASE_COMMIT=<40hex>` создаёт локальный кандидат
только из указанного неизменяемого коммита. Кандидат нельзя собирать вручную из
рабочего дерева и называть официальным.

Сценарий сборки требует, чтобы `HEAD` точно совпадал с `RELEASE_COMMIT`, а
рабочая копия не содержала отслеживаемых или неотслеживаемых изменений.
Фактически выполняемый сценарий сборки побайтно сверяется с его копией в коммите выпуска. Зависимости
загружаются и проверяются в отдельном кэше npm для снимка и в кэше модулей Go
`/var/tmp/guard-daemon-release-go-mod-v1` с исключительным доступом; кэш Go
использует стабильный путь для воспроизводимости и удаляется сценарием после
сборки. Если путь уже занят или остался после аварийного завершения, сборка
безопасно завершается с ошибкой.
Окружение Python изолируется.

Двоичный файл выпуска компилируется официальным дистрибутивом Go 1.26.5. Nix
может предоставлять остальные инструменты проверки, но изменённую версию Go из Nix
нельзя ставить первой в `PATH`: локальные пути хранилища меняют значения по
умолчанию во время выполнения и байты двоичного файла. Сценарий сборки
обнаруживает такие пути после сборки и отклоняет кандидата.

Результат цели является только локальным кандидатом для окончательной
независимой проверки в задаче 11. До решения `РАЗРЕШИТЬ ВЫПУСК` его запрещено
публиковать. Эта процедура не создаёт тег, не выполняет `push`, не создаёт GitHub
Release, не развёртывает контракт и не отправляет транзакции в основную сеть.

## Модель репозиториев

`origin` используется как рабочее ответвление. `upstream` используется только
как источник для `fetch` и контролируемой синхронизации. Сценарии репозитория не
изменяют удалённые репозитории, никогда не выполняют `push`, не создают тег и не
публикуют выпуск.

Оператору рекомендуется запретить случайный `push` в `upstream` локальной
настройкой:

```sh
git remote set-url --push upstream DISABLED
git remote -v
```

Эти команды выполняет и проверяет оператор. Агент их не выполняет. В публичное
подтверждение не включаются реальные URL `origin` или `upstream`.

## Предварительные условия

Кандидат строится только после выполнения всех условий:

- задачи 01-10 имеют статус `DONE`, а отчёты их независимой проверки изучены;
- в отчётах и реестре нет открытых замечаний критического (`Critical`) или
  высокого (`High`) уровня;
- полный CI прошёл для выбранного коммита;
- оператор предоставил подтверждение обязательных проверок, правил ветки и
  работы Dependabot без закрытых данных по правилам [evidence/README.md](evidence/README.md);
- выбранный коммит выпуска уже существует как неизменяемый коммит Git;
- коммит выпуска задан полным 40-символьным SHA-1 в нижнем регистре, а не
  именем ветки, тегом, сокращённым SHA или значением `HEAD`;
- в коммит входят файлы фиксации версий зависимостей, контрактный артефакт,
  схема манифеста, русскоязычные руководства и отчёты независимой проверки
  задач 01-10.

Подготовительные проверки:

```sh
npm ci
make security-validation
make documentation-check
make operations-check
make operations-rehearsal
```

`operations-rehearsal` не использует рабочие RPC или рабочие секретные данные.
Тест развёртывания подписывает локальным тестовым ключом и отправляет транзакцию
только в одноразовый Anvil; команда активации рабочей среды и публичная сеть не
используются.

## Выбор коммита

Оператор фиксирует полный идентификатор уже проверенного коммита и убеждается,
что он соответствует объекту коммита:

```sh
git rev-parse --verify '<40hex>^{commit}'
git show --no-patch --format='%H' '<40hex>'
```

Обе команды должны вывести один и тот же `<40hex>`. Значение передаётся явно:

```sh
make release-candidate RELEASE_COMMIT=<40hex>
```

Цель отклоняет отсутствующий или неканонический идентификатор, несовпадение
`HEAD` и любое изменение рабочей копии. Она читает снимок непосредственно из
указанного коммита и не подмешивает содержимое рабочего дерева. Наличие
локального объекта обязательно; Git ничего не загружает из сети.

## Детерминированная сборка

Цель вызывает собственный генератор репозитория на Python и создаёт
ровно один каталог:

```text
dist/release/<commit>/
```

`dist/` игнорируется Git. Генератор не получает секрет подписи, не выполняет
вызовы EVM и не развёртывает контракт. `npm ci` и Go могут обращаться только к
обычным реестрам закреплённых зависимостей. Двоичный файл собирается для `linux/amd64` с
`CGO_ENABLED=0`, `-trimpath`, отключённой меткой VCS и пустым идентификатором
сборки Go. Исходный tar-архив является точным выводом
`git archive --format=tar` с фиксированным префиксом
`guard-daemon-<commit>/`: его нельзя перепаковывать, дополнять или
сжимать после создания.

Метаданные сериализуются канонически с неизменным порядком ключей и массивов.
В них не включаются время сборки, имя узла, имя пользователя, текущий каталог
или значения окружения. SBOM имеет формат CycloneDX 1.6 JSON. Документ о
происхождении имеет формат одного неподписанного документа `in-toto Statement` со
сведениями SLSA Provenance v1, записанного как JSONL. Полный состав описан в
[artifacts.md](artifacts.md).

SBOM строится из `package-lock.json`, списка модулей и `go mod graph`, поэтому
сохраняет прямые и транзитивные связи Go, включая закреплённые замены `replace`.
Документ о происхождении фиксирует SHA-256 фактически выполненного сценария
сборки из архива исходного кода.

## Проверка кандидата

После сборки выполняются пункты [checklist.md](checklist.md). Обязательны две
чистые независимые сборки одного коммита, побайтовое совпадение файлов, проверка
`SHA256SUMS`, проверка схем JSON и поиск секретных данных во всём созданном
каталоге.

Расхождение хотя бы одного байта блокирует кандидата. Исправление выполняется в
новом коммите, после чего выбирается новый `<40hex>` и все проверки повторяются.
Содержимое уже проверенного каталога не исправляется вручную.

## Манифест развёртывания

Кандидат содержит только `rescuer-manifest.schema.json`. Официальный манифест
развёртывания с коммитом выпуска создаётся оператором или отдельным CI без
постоянных ключей только после появления проверенного кандидата. Манифест нельзя
создавать заранее, подменять им метаданные выпуска или добавлять в кандидат
задним числом.

Создание манифеста не означает разрешения на активацию в основной сети. Сеть,
назначение, `sponsor`, идентификатор среды выполнения, ограниченное пополнение и
чтение состояния после развёртывания проверяются отдельно по руководству по
развёртыванию. Агент не выполняет эти действия.

## Подпись и публикация

Текущие GitHub Actions имеют только `contents: read`, не запрашивают токен OIDC
и ничего не подписывают. Неподписанный документ о происхождении фиксирует
заявленные исходные данные и результаты, но не подтверждает подлинность сведений
о сборщике.

Подписывать артефакты разрешено только одним из способов:

- в отдельном CI без постоянных ключей после проверки точных правил
  идентификации OIDC;
- оператором вне агента и вне среды репозитория.

Закрытый ключ и секрет подписи либо токен OIDC нельзя передавать агенту,
сохранять в репозитории или добавлять в метаданные выпуска. `SHA256SUMS`
выявляет изменение файлов, но не подтверждает подлинность издателя и не заменяет
подпись.

После локальной подготовки кандидат остаётся непубликуемым материалом для задачи 11.
Только независимое решение по задаче 11 `РАЗРЕШИТЬ ВЫПУСК` позволяет оператору
начать отдельную процедуру подписи и публикации. Даже после этого тег, `push`,
GitHub Release и активация в основной сети требуют отдельных явных действий оператора
и не выполняются сценариями выпуска.
