# Автоматические сборки в GitHub Releases

Workflow `.github/workflows/release.yml` публикует сборки по явно отправленному
тегу версии. Он не развёртывает контракт, не запускает демон и не получает
операторские ключи или рабочие RPC.

Эти архивы предназначены для распространения сборок исходного кода. Они **не
являются официальным кандидатом**, описанным в [artifacts.md](artifacts.md), не
содержат его SBOM и сведений о происхождении и не заменяют независимую проверку,
подпись или разрешение на эксплуатацию из [process.md](process.md).

## Платформы и содержимое

Сборка Go 1.26.9 выполняется из `./cmd/guard-daemon` с `CGO_ENABLED=0` для
Linux, macOS (`darwin`) и Windows, для `amd64` и `arm64`. Бинарник содержит полный
SHA коммита, доступный через `--version`.

Поддерживаемый профиль эксплуатации остаётся **Linux/amd64 с systemd**.
Остальные платформы экспериментальны: успешная компиляция не подтверждает
работоспособность службы. В частности, Windows не реализует межпроцессное
ограждение состояния; рабочий запуск безопасно отклоняется.

Каждый `.tar.gz` (Linux/macOS) или `.zip` (Windows) содержит бинарник, лицензию,
README, заглушку `.env.example`, каталог документации, файлы упаковки службы,
канонический контрактный артефакт и схему манифеста. Официальные адреса,
операторские манифесты и рабочие данные не добавляются.

## Запуск процесса публикации

Сначала закоммитьте и отправьте изменения, включая workflow. После необходимых
проверок оператор явно выбирает новую версию:

```sh
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
```

Номер версии выбирается вручную. После отправки тега автоматически выполняются:

1. проверка формата версии, модулей Go, тестов и `go vet`;
2. шесть сборок и упаковка архивов;
3. создание `SHA256SUMS`;
4. создание черновика GitHub Release с автоматически сгенерированными заметками;
5. загрузка всех файлов и публикация только после успешной загрузки.

Тег вида `v1.1.0-rc.1` создаёт prerelease, который не помечается Latest.
Повторный запуск может продолжить загрузку черновика. Опубликованный релиз не
перезаписывается; для изменений нужен новый тег.

Используется встроенный `GITHUB_TOKEN`. Все проверки и сборки имеют только
`contents: read`; единственное исключение — отдельный job `publish` с
`contents: write`, запускаемый только по пушу тега `v*`. Собственных секретов,
OIDC и ключей подписи нет. Политики GitHub должны разрешать Actions и указанное
право публикации.

## Проверка загруженных файлов

Поместите `SHA256SUMS` рядом с архивами. На Linux:

```sh
sha256sum --ignore-missing -c SHA256SUMS
```

На macOS вычислите `shasum -a 256 <archive>` и сравните с соответствующей строкой.
Контрольная сумма подтверждает совпадение файла со списком, но не подлинность
издателя.
