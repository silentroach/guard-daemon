# Аттестация кандидата выпуска и манифеста развёртывания

## Цель

Аттестация связывает четыре объекта: неизменяемый commit выпуска, точные байты
канонического артефакта, транзакцию развёртывания и состояние контракта в
финализированной цепочке. Ни доверие к одному RPC, ни успешный receipt, ни
совпадение одного getter сами по себе эту связь не доказывают.

## Кандидат выпуска

`release-candidate.json` создаётся только после появления неизменяемого commit
выпуска. Для deployment существенны:

- полный 40-символьный commit из строчных шестнадцатеричных символов;
- SHA-256 точных байтов `artifacts/contracts/RescuerV2.json` в форме
  `sha256:<64 строчных шестнадцатеричных символа>`.

Смысловая форма записи:

```json
{
  "releaseCommit": "<40 строчных шестнадцатеричных символов>",
  "artifacts": {
    "contract": {
      "path": "RescuerV2.json",
      "sha256": "sha256:<64 строчных шестнадцатеричных символа>"
    }
  }
}
```

Это сокращённое описание обязательной связи, а не полная схема и не разрешение
вручную изготовить метаданные. Строгий parser проверяет полный объект кандидата,
его платформу и фиксированный набор артефактов. Неизвестные поля, повторяющиеся JSON-ключи, сокращённый commit и
несовпадающий digest должны приводить к отказу до RPC и чтения ключа.

## Официальный манифест

Для публичного развёртывания манифест версии `1` обязан содержать:

- `source.kind` со значением `git-commit`;
- `source.value`, точно равный полному commit из release candidate;
- `artifact.sha256`, точно равный digest из release candidate и digest
  прочитанных байтов канонического артефакта;
- chain ID, адрес контракта, hash и номер блока и hash транзакции развёртывания;
- версию компилятора и точные настройки;
- Keccak-256 и длину связанного runtime;
- аргументы конструктора и неизменяемые `destination`, `self`, `sponsor`.

Любой другой `source.kind` не удовлетворяет требованиям официального кандидата
выпуска. Происхождение нельзя переименовывать в `git-commit` без повторного
создания манифеста из проверенного выпуска.

Манифест не содержит ключ, подпись, RPC URL, authorization tuple или
операторские секреты. Путь манифеста не должен совпадать с артефактом, release
candidate или операторской конфигурацией, в том числе через symbolic/hard link.
Сам manifest и его заранее существующий родитель должны находиться вне candidate
и Git worktree; родитель не может быть symbolic link.

## Уровни проверки

### 1. Локальная воспроизводимость

`npm run artifacts:verify` повторно компилирует закреплённый исходный код и
побайтно сравнивает артефакт. Затем вычисляется SHA-256 файла и сверяется с
release candidate. Проверка commit выполняется до сетевого доступа.

### 2. Ограниченное построение транзакции

Deployment CLI допускает broadcast только для chain ID `1`, `56`, `137` и
локального `31337`, проверяет роли, строит точные данные конструктора и
явно устанавливает `gasLimit`, `maxFeePerGas` и `maxPriorityFeePerGas`. Он
отклоняет транзакцию, если `gasLimit * maxFeePerGas` превышает
`max-total-cost-wei`. CLI не определяет модель дополнительной комиссии сети;
оператор обязан отдельно заблокировать сеть, где полная стоимость не ограничена
полями подписанной транзакции.

До отправки точная подписанная транзакция сохраняется в новом recovery record с
режимом `0600`. Manifest создаётся эксклюзивно только после receipt и
предварительного чтения. Для production registry фиксирован как
`/var/lib/guard-daemon-operator/deployment-recovery` (`0700 root:root`);
локальная chain ID `31337` требует явный временный `--recovery-directory`.
Canonical identity и device/inode registry и родителя manifest повторно
проверяются перед записью. Production manifest создаётся только в фиксированном
каталоге `/var/lib/guard-daemon-operator/deployment-manifests` (`0700
root:root`), затем оператор отдельно устанавливает проверенную копию в `/etc`.
Существующий record той же пары chain+sponsor независимо от commit или
существующий manifest блокирует новый запуск, чтобы неоднозначный исход не
превратился в повторный deployment.

Production использует только аутентифицированные root-owned candidate/tooling и
не читает Git metadata. Для локальной chain ID `31337` проверка checkout
fail-closed отклоняет repository-local `info/attributes`, `assume-unchanged` и
`skip-worktree`, включая повторную проверку index bits после канонического
`git archive`. Production RPC URL поступает только из `DEPLOYMENT_RPC_URL`;
`--rpc-url` оставлен только для локального `31337` и режима плана, чтобы
credentials не попадали в argv.

### 3. Предварительное чтение одним RPC

После receipt deployment script через тот же RPC сверяет runtime и getter-функции
по блоку развёртывания и только затем атомарно публикует манифест. Это полезная
самопроверка против ошибки конструктора или адреса, но единственный RPC остаётся
недоверенным. Такой результат нельзя называть окончательной attestation.

### 4. Эксплуатационная аттестация двумя поставщиками

Окончательный gate выполняет сам демон при `DRY_RUN=false` и
`EMERGENCY_STOP=true` без приватных ключей. Минимум два независимо настроенных
HTTP-поставщика чтения должны иметь разные endpoint fingerprint, домены доверия
и экземпляры клиента. Они обязаны согласовать общий финализированный номер и
hash блока.

На этом общем состоянии каждый поставщик подтверждает:

1. Ожидаемый chain ID.
2. Финализацию блока развёртывания и его hash.
3. Точную CREATE-транзакцию и непредварительный успешный receipt.
4. Адрес созданного контракта.
5. Полное совпадение runtime со связанным каноническим артефактом.
6. `destination`, `self` и `sponsor` по вызовам, закреплённым hash блока.

RPC отправки не участвует в кворуме чтения. Расхождение высоты разрешается
только переходом к общему более низкому финализированному блоку с тем же hash у
обоих поставщиков. Отсутствующий или повреждённый ответ, timeout, pending
transaction, неуспешный receipt или расхождение любого поля означает отказ.

## Свидетельство

Безопасный пакет свидетельств содержит release candidate, полный commit,
SHA-256 артефакта и манифеста, публичные transaction/block hashes и
обезличенный результат startup gate. Он не содержит RPC URL с credentials,
сырые подписанные транзакции до включения, ключи, подписи или данные
авторизации.

Положительная локальная проверка или чтение через один RPC не заменяет запуск
демона с двумя независимыми поставщиками. Даже прохождение всех проверок не
гарантирует победу в гонке за скомпрометированный source и не означает
готовность к mainnet.
