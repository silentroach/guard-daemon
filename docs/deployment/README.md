# Развёртывание RescuerV2

Этот каталог разделяет безопасную локальную проверку, операторское действие в
публичной сети и независимую эксплуатационную аттестацию. Ни один документ не
утверждает готовность к mainnet и не подтверждает, что публичное развёртывание
или локальная репетиция уже выполнены.

## Порядок чтения

1. [`local-verification.md`](local-verification.md) — проверка артефакта, план
   без отправки и локальный Anvil.
2. [`manifest-attestation.md`](manifest-attestation.md) — связь commit выпуска,
   артефакта, манифеста и состояния сети.
3. [`operator-activation.md`](operator-activation.md) — процедура, которую в
   публичной сети выполняет только оператор.
4. [`../migration/delegation.md`](../migration/delegation.md) — граница смены
   реализации и делегации EIP-7702.
5. [`../migration/rollback-emergency.md`](../migration/rollback-emergency.md) —
   emergency stop, сохранение свидетельств и ограничения rollback.

## Обязательные границы

- Агент не отправляет транзакции, не пополняет sponsor, не получает ключи и не
  выполняет команды активации публичной сети.
- Без `--broadcast` deployment CLI не использует RPC или ключ и требует только
  chain ID, `destination` и `sponsor`; значения `DEPLOYMENT_RPC_URL` и
  `DEPLOYER_PRIVATE_KEY` в этом режиме не читаются.
- Режим с отправкой допустим только с обязательными лимитами
  `gas-limit`, max fee, priority fee и полной стоимости газа, а также проверки
  полного каталога `release-candidate.json` и канонического recovery registry.
  Production RPC передаётся только через `DEPLOYMENT_RPC_URL`, а не через argv;
  `--rpc-url` допустим только для локальной chain ID `31337` или игнорируемого
  плана без отправки.
- Официальный манифест связывается с полным commit выпуска через
  `source.kind=git-commit`; SHA-256 артефакта в нём совпадает с release
  candidate.
- Чтение через единственный RPC после развёртывания предварительное. Перед
  включением подписания демон должен стартовать с `DRY_RUN=false` и
  `EMERGENCY_STOP=true`, без ключей, и провести аттестацию двумя независимыми
  поставщиками на общем финализированном блоке.
- Подписанная deployment-транзакция сохраняется в recovery record с режимом
  `0600` до broadcast. Неоднозначный результат запрещает новый deployment до
  сверки оператором. Для chain ID `1`, `56` и `137` registry всегда равен
  `/var/lib/guard-daemon-operator/deployment-recovery`, имеет режим `0700` и
  владельца `root:root` и не переопределяется. CLI повторно сверяет canonical
  path, device/inode, режим и владельца непосредственно перед lock и записью.
  Только для локальной chain ID `31337` обязателен `--recovery-directory` с
  заранее созданным временным каталогом `0700` вне candidate и Git worktree.
- Production запускается только из аутентифицированных root-owned каталогов
  `/usr/lib/guard-daemon/deployment/<commit>` и
  `/usr/lib/guard-daemon/candidates/<commit>`. Обычный checkout и mutable
  `node_modules` запрещены; секреты передаются только новому процессу после
  отдельного preflight без секретов.
- Локальная chain ID `31337` проверяет чистый checkout и отдельно отклоняет Git
  index flags `assume-unchanged` и `skip-worktree`; одного пустого `git status`
  недостаточно.
- Скомпрометированный source-ключ остаётся скомпрометированным. Развёртывание и
  делегация не гарантируют победу в гонке и не разрешают повторно использовать
  legacy EOA.

## Блокирующие условия

Публичная отправка заблокирована, если проверяемый release candidate, CLI,
пределы стоимости или происхождение `git-commit` не соответствуют этим
документам. Постоянные хранилища watcher и бюджета также не поддерживают
безопасную смену `rescuer` на месте. Поэтому документация задаёт проверяемые
условия активации, но сама по себе не является разрешением на live-действия.
