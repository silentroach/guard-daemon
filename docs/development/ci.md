# Обязательные проверки разработки

GitHub Actions не устанавливает и не вызывает Nix. CI работает на
`ubuntu-24.04`. Текущие точные версии основных инструментов:

- Go `1.26.5`;
- Node.js `24.18.1`;
- npm `11.16.0`;
- Python `3.14.6`;
- actionlint `1.7.12`;
- ShellCheck `0.11.0`;
- govulncheck `1.1.4`;
- gitleaks `8.30.1`;
- Foundry `1.7.1`;
- Slither `0.11.6` и crytic-compile `0.4.2`;
- solc `0.8.36`, коммит `8a079791`;
- PyYAML `6.0.3` для проверки правил репозитория.

Инструменты Node.js также закреплены в `package-lock.json`: TypeScript `6.0.3`,
tsx `4.23.1`, ESLint `10.8.0`, typescript-eslint `8.65.0` и Prettier `3.9.6`.

Официальные компоненты GitHub Actions закреплены одновременно версией и полным
SHA-идентификатором коммита:

- `actions/checkout` `v7.0.1`:
  `3d3c42e5aac5ba805825da76410c181273ba90b1`;
- `actions/setup-go` `v7.0.0`:
  `b7ad1dad31e06c5925ef5d2fc7ad053ef454303e`;
- `actions/setup-node` `v7.0.0`:
  `820762786026740c76f36085b0efc47a31fe5020`;
- `actions/setup-python` `v7.0.0`:
  `5fda3b95a4ea91299a34e894583c3862153e4b97`;
- `actions/dependency-review-action` `v4.9.0`:
  `2031cfc080254a8a887f58cffee85186f0e49e48`.

Архивы ShellCheck, Foundry и отдельный solc проверяются по закреплённым SHA-256.
Foundry устанавливается напрямую из архива выпуска без `foundryup`.
Зависимости Python устанавливаются только из пакетов формата wheel с
закреплёнными хешами. Контрактные тесты используют Prague EVM и усиленный профиль
`ci`: 10 000 прогонов каждого фаззинг-теста и 1 000 прогонов проверки инвариантов
глубиной 256 вызовов.

Локально можно использовать необязательное окружение `nix develop`, но все
приведённые ниже команды являются обычными командами репозитория и не зависят
от Nix.

Установите зависимости Node.js без изменения `package-lock.json`:

```sh
npm ci
```

Ни одна из следующих команд не выполняет развёртывание в промышленной среде, не
использует операторские ключи и не обращается к внешнему RPC. Тесты развёртывания
запускают только тестовый Anvil через интерфейс обратной петли и отправляют в
него детерминированные локальные транзакции.

## Команды

Базовая локальная проверка:

```sh
make check
```

Полная проверка безопасности в рамках задачи 09, включая статический анализ,
интеграционные тесты с имитацией атак, ограниченный фаззинг, проверку правил репозитория и две
чистые сборки артефактов:

```sh
make security-validation
```

Для `ci-policy` заранее установите зависимости с закреплёнными хешами:

```sh
python3 -m pip install --only-binary=:all: --require-hashes \
  --requirement test/ci/requirements.txt
```

Отдельные группы проверок:

```sh
make format-check
make workflow-lint
make go-ci
make node-ci
make vuln
make audit
make secret-scan
make contracts-static
make adversarial-test
make fuzz-test
make ci-policy
make reproducibility-check
```

## Проверки эксплуатации и выпуска

Интерфейс репозитория включает следующие цели:

```sh
make documentation-check
make operations-check
make operations-rehearsal
make release-candidate RELEASE_COMMIT=<40hex>
```

`documentation-check` проверяет ссылки, русский язык и соответствие
документации схеме. `operations-check` проверяет эксплуатационную
политику, сгенерированные метаданные, схемы и контрольные суммы.
`operations-rehearsal` выполняет только локальный сценарий без отправки
транзакций в публичную сеть. `release-candidate` принимает только полный
идентификатор неизменяемого коммита и создаёт детерминированный каталог
`linux/amd64` с `CGO_ENABLED=0` по процедуре
[../release/process.md](../release/process.md).

Процесс проверки воспроизводимости дважды создаёт кандидата выпуска из точного
коммита, сравнивает результаты и сканирует оба каталога и вложенные tar-архивы на
секреты. Процессы GitHub Actions имеют только разрешение `contents: read`, не
получают токен OIDC и не подписывают артефакты. До решения по задаче 11 публикация кандидата
запрещена; эти цели не создают тег и выпуск в GitHub, не выполняют `push` и
действия в основной сети.

Исправление форматирования Go, TypeScript и Solidity:

```sh
make format
```

Локальная компиляция Solidity создаёт игнорируемые артефакты в `build/contracts`:

```sh
make contracts-build
make contracts-test
```

## Обязательные проверки ветки

Для защищённой основной ветки следует требовать следующие обязательные проверки:

- `CI / Formatting`;
- `CI / Go Checks`;
- `CI / TypeScript and Contract Checks`;
- `CI / Adversarial Go Integration`;
- `CI / Bounded Go Fuzzing`;
- `CI / Isolated Local Deployment Tests`;
- `Security / Vulnerabilities`;
- `Security / New Dependency Review` для запросов на слияние;
- `Security / Secrets`;
- `Security / Repository Policy`;
- `Security / Reproducible Artifacts`;
- `Security / Solidity Static Analysis`.

Рекомендуемые правила защиты ветки:

- запрет прямого `push` и `force-push` в основную ветку;
- минимум одно одобрение запроса на слияние от участника, не являющегося автором;
- сброс одобрений после изменения набора правок;
- обязательное завершение всех обсуждений проверки кода;
- запрет слияния при незавершённых или неуспешных обязательных проверках;
- запрет автоматического слияния обновлений зависимостей с изменением основной
  версии без успешных проверок и ручной проверки безопасности;
- ограничение прав обхода набора правил минимальным списком операторов.

Оператор включает набор правил в GitHub. Само наличие этого документа не
доказывает, что правила включены: до начала задачи 11 их необходимо проверить через
GitHub API и сохранить общедоступное подтверждение без токенов и приватных
данных.

## Кеши CI

CI использует встроенные кеши `actions/setup-go` и `actions/setup-node` только
для модулей и сборки Go, а также загружаемых пакетов npm. Кеш Foundry отключён,
тесты не обращаются к внешнему RPC. Локальный набор тестов развёртывания
использует только Anvil на `127.0.0.1`. `.env`, файлы ключей, сгенерированные
манифесты развёртывания и иное локальное состояние не входят в пути кеша.
Процессы GitHub Actions имеют только разрешение `contents: read`, не используют
окружения GitHub и не получают секреты рабочей среды.
