# Модель безопасности RescuerV2

## Назначение

`RescuerV2` исполняется как код EIP-7702 delegated EOA и переводит токены или
ETH только на неизменяемый `destination`. Контракт не делает
скомпрометированный source безопасным: владелец source-ключа может заменить
делегацию, подписать конкурирующую authorization или опередить
rescue-транзакцию.

## Контекст исполнения EIP-7702

Конструктор выполняется по адресу реализации и сохраняет этот адрес в
неизменяемом поле `self`. При последующем делегированном исполнении
`address(this)` равен source EOA, а не адресу реализации. `_verifyDelegation`
читает код source, требует точный 23-байтовый designator
`0xef0100 || implementation` и сравнивает implementation с `self`.

Проверка предотвращает продолжение операции через этот код при ошибочной
делегации. Она не способна остановить произвольный код другой реализации,
которую атакующий назначил с помощью скомпрометированного source-ключа.

## Роли и получатель

- `destination` получает все активы из `sweepAll` и `sweepEth` и не задаётся
  вызывающей стороной;
- `sponsor` оплачивает транзакции и является единственной вызывающей стороной
  для `executeAndSweep`;
- конструктор отклоняет нулевые роли и совпадение
  `destination == sponsor`.

`sweepAll` и `sweepEth` доступны любой стороне: посторонний вызов может только
раньше перевести активы на тот же фиксированный `destination`.
`executeAndSweep` намеренно принимает `target` и `calldata` от доверенного
sponsor, потому что интерфейсы получения активов различаются. Список запрещённых
селекторов не защищает от fallback, прокси и совпадений селекторов.
Компрометация sponsor поэтому требует emergency stop и новой аттестованной
реализации с другим sponsor; текущие постоянные хранилища не поддерживают такую
смену на месте.

## Делегация для конкретной операции

Отдельной профилактической транзакции обновления делегации нет. Демон
прикладывает новую authorization только к конкретной rescue operation, которая
в той же EIP-7702 транзакции вызывает `sweepAll`, `sweepEth` или разрешённый
`executeAndSweep`. Если перемещать конкретный актив не требуется, делегация не
обновляется.

Такой порядок исключает отдельный вызов source только ради делегации, но не
устраняет гонку. Атакующий может первым использовать тот же nonce, установить
другую реализацию и заставить внешнюю транзакцию исполнить чужой код. Поэтому
receipt сам по себе не доказывает rescue; обязательны финализированная проверка
текущей делегации и postcondition конкретного актива.

## Недоверенные токены и обратные вызовы

`balanceOf` принимается только при успешном `staticcall` с результатом ровно
32 байта. `transfer` использует правило необязательного возвращаемого значения:

- пустой результат означает совместимый успех;
- ровно 32 байта со значением `1` означают успех;
- `false`, неканонический `bool`, другая длина и revert означают ошибку всей
  операции.

Такой результат остаётся заявлением недоверенного контракта токена и не
доказывает экономическую стоимость. Поэтому демон классифицирует итог любого
ERC-20 только как `token-reported`, даже если адрес известен и имеет доверенную
операторскую оценку ценности.

Обратный вызов токена может повторно вызвать доступную всем sweep-функцию, но
получатель останется тем же. Он не может войти в `executeAndSweep`, поскольку
его `msg.sender` не равен sponsor. Reentrancy guard в storage намеренно не
используется: при EIP-7702 storage принадлежит source EOA, и новый служебный slot
создал бы риск коллизии с другой реализацией.

## События и поверхность кода

`Swept(source, token, destination, amount)` фиксирует source, token,
destination и заявленный amount. Для ETH поле token равно нулевому адресу.
Событие не является доказательством экономической ценности токена.

Контракт Permit и путь его развёртывания удалены. Единственный CLI
`scripts/deployRescuerV2.ts` использует канонический артефакт и без явного
`--broadcast` строит локальный план без RPC, ключа и отправки. Локальная проверка
повторяет закреплённую компиляцию и побайтно сравнивает артефакт; инструкция
находится в `docs/deployment/local-verification.md`.

Официальный deployment manifest должен связывать SHA-256 канонического
артефакта с полным commit выпуска из `release-candidate.json` и использовать
`source.kind=git-commit`. Одиночное RPC-чтение deployment script является только
предварительной проверкой. Эксплуатационная аттестация выполняется демоном без
ключей при `DRY_RUN=false` и `EMERGENCY_STOP=true` через два независимых
поставщика на общем финализированном блоке.

## Воспроизводимость и измерения

Контракт компилируется `solc 0.8.36` для Prague с optimizer `runs=200`, без
CBOR metadata и metadata hash. `foundry.toml` и TypeScript-компилятор используют
одинаковые параметры. Размер creation/runtime bytecode и измерения газа
получаются командами `forge build --sizes` и `forge test --gas-report`; это
эксплуатационные измерения, а не доказательство безопасности.

Для закреплённого канонического артефакта `forge build --sizes` сообщил 2 790
байт creation bytecode и 2 431 байт runtime bytecode. `forge test --gas-report`
сообщил 581 683 gas для тестового развёртывания и диапазон 1 221–22 715 gas для
распознанных вызовов `sweepAll`. Отчёт не учитывает полную стоимость каждого
делегированного сценария EIP-7702, поэтому числа нельзя использовать как fee
policy без моделирования конкретной транзакции.

`Slither 0.11.6` анализирует рабочий исходный код отдельно от атакующих макетов.
В проверенном отчёте отсутствовали findings уровней Critical и High. Оставшиеся
сообщения относились к необходимым низкоуровневым вызовам ERC-20 и
assembly-декодированию, вызовам токенов в цикле и событию после успешного
внешнего вызова. Цикл ограничивается операционной политикой и бюджетом; модель
обратных вызовов покрыта тестами и не позволяет изменить фиксированный
получатель.

Эти результаты не утверждают готовность к mainnet и не подтверждают успешную
репетицию публичного развёртывания или миграции.
