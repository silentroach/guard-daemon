# Политика исходящих соединений

Базовый unit ограничивает семейства сокетов значениями `AF_UNIX`, `AF_INET` и
`AF_INET6`, но намеренно не содержит `IPAddressDeny=`. Это ограничение семейств
не является межсетевым экраном и не ограничивает адрес назначения.

## Требуемые назначения

Для каждой включённой сети `<N>` демону нужны три логические роли RPC:

| Роль | Поля | Схема в рабочей среде | Назначение |
|---|---|---|---|
| Первый источник чтения | `RPC_READ_1_HTTP_<N>`, `RPC_READ_1_WS_<N>` | `https`, `wss` | HTTP для согласованных чтений и аттестации; WebSocket для предварительных событий |
| Второй источник чтения | `RPC_READ_2_HTTP_<N>`, `RPC_READ_2_WS_<N>` | `https`, `wss` | Независимое HTTP-чтение и резервное подключение событий |
| Отдельная отправка | `RPC_BROADCAST_HTTP_<N>` | `https` | Только отправка в рабочем режиме |

Демон требует разные канонические HTTP URL, разные WebSocket URL и разные
настроенные домены доверия у двух источников чтения. URL отправки обязан
отличаться от обоих HTTP URL чтения. RPC отправки не участвует в согласовании
финализированного состояния. В `DRY_RUN=true` поле отправки запрещено; при
`DRY_RUN=false` оно обязательно, в том числе при `EMERGENCY_STOP=true`, хотя в
аварийном режиме компонент отправки не создаётся.

Схемы `http` и `ws` принимаются реализацией для локальных испытаний. В
рабочей среде разрешены только `https` и `wss`. Не ослабляйте проверку
сертификата и не подменяйте независимые источники одним посредником.

Если URL используют имена, службе также нужен доступ к утверждённому
рекурсивному DNS-серверу. Разрешение имён DNS не должно открывать прочий исходящий трафик.

## Граница применения политики

Приложение проверяет синтаксис и различие настроенных URL, но не реализует
список разрешённых исходящих имён. Значение `RPC_READ_1_TRUST_DOMAIN_<N>` —
операторская метка независимости, а не правило межсетевого экрана. systemd и
обычный узловой межсетевой экран применяют правила к IP-адресам, UID или cgroup,
а не доказывают имя из URL.

Поэтому запись имени RPC в комментарии к правилу, наборе записей DNS или списке настроек
не гарантирует соблюдение политики. Если несколько служб используют общий IP,
разрешение этого IP также не ограничивает доступ конкретным именем. TLS
проверяет имя, а IP-правило ограничивает направление соединения. Изменение
ответов DNS провайдера требует контролируемого обновления всех IPv4- и
IPv6-адресов в списке разрешённых адресов.

## Правило для хоста

На рабочем хосте примените исходящий запрет по умолчанию только к
процессам службы, затем разрешите:

- все текущие IPv4- и IPv6-адреса обоих HTTP и обоих WebSocket источников чтения
  каждой включённой сети на их фактических портах;
- все текущие IPv4- и IPv6-адреса отдельного RPC отправки на его фактическом
  порту, только если используется `DRY_RUN=false`;
- адреса утверждённого DNS-сервера на TCP и UDP 53, только если URL
  содержат имена;
- ответный трафик для уже установленных соединений, необходимый выбранному
  межсетевому экрану.

Не разрешайте исходящие TCP-соединения на порт 443 для любых адресов: это
отменяет ограничение назначения. Не разрешайте
исходящий трафик по UID `root`, потому что демон от `root` не запускается.

Статический системный пользователь создаётся при установке, но его числовой UID
выбирает целевая система. Получайте его на хосте:

```bash
id -u guard-daemon
systemctl show guard-daemon.service --property=ControlGroup --value
```

Межсетевой экран может привязать правила к этому UID. Средство на основе eBPF
может привязать их к cgroup, возвращённой systemd. Выберите один механизм,
поддерживаемый операционной системой, и обеспечьте запрет по умолчанию для этой
службы. Не добавляйте общий `IPAddressDeny=any` в базовый unit: список
назначений зависит от операторских RPC, а неполный список приведёт к сбою
запуска и сверки.

## Проверка

После каждого изменения RPC или адресов провайдера:

1. Получите A и AAAA через утверждённый DNS-сервер и сопоставьте результат
   со списком разрешённых адресов; не записывайте закрытые URL в отчёт.
2. Запустите службу сначала без отправки и подтвердите, что оба источника чтения
   проходят согласование, WebSocket открывается, а `/healthz` достигает
   `healthy_idle`.
3. Проверьте счётчики межсетевого экрана по UID или cgroup и убедитесь, что нет
   соединений к другим назначениям.
4. В рабочем режиме отдельно подтвердите доступность назначения отправки без
   отправки реальной транзакции в рамках автоматизированной проверки.
5. Заблокируйте HTTP-направление одного источника чтения в испытательной среде и
   убедитесь, что согласование не может использовать только второй источник и
   возникает `rpc_degraded`.

Конкретные правила nftables, средства облачной сети и программы eBPF зависят от
адресов RPC и целевой системы, поэтому репозиторий не публикует фиктивный
универсальный набор команд. Политика считается внедрённой только после проверки
фактических правил и их счётчиков на целевом хосте.
