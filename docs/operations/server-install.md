# Первая установка на общий сервер

Профиль рассчитан на Linux/amd64 с systemd и cgroup v2. Он устанавливает службу
в существующую раскладку `/usr/lib/guard-daemon`, `/etc/guard-daemon` и
`/var/lib/guard-daemon`. Установка выполняется один раз, до заполнения конфигурации.

## Установка выпуска

Скачайте архив выбранной версии `guard-daemon_<version>_linux_amd64.tar.gz` и
`SHA256SUMS` со страницы GitHub Release. В отдельном каталоге проверьте архив:

```bash
set -euo pipefail
sha256sum --ignore-missing --check --strict SHA256SUMS
```

Получите полный коммит выбранного тега, распакуйте проверенный архив в отдельный
каталог и запустите установщик из доверенного набора инструментов:

```bash
set -euo pipefail
sudo bash scripts/install-systemd.sh /path/to/extracted-release FULL_40_HEX_COMMIT
```

В `v0.0.1` каталога `scripts` в архиве ещё нет: установщик и два служебных скрипта
нужно взять из проверенной рабочей копии вместе с `packaging/systemd`.
Последующие архивы включают их. Установщик сверяет `--version` с указанным
коммитом; проверку контрольной суммы архива выполняют до запуска установщика.
Список SHA-256 подтверждает целостность загрузки, а доверие к издателю определяется
источником полученных файлов.

Установщик создаёт пользователя, каталоги, unit и профиль общего сервера,
проверяет учётную запись и выполняет `systemd-analyze verify`. Служба остаётся
выключенной до заполнения конфигурации. Повторная установка поверх существующего
unit или выпуска отклоняется. Обновление выполняется отдельно по
[руководству оператора](runbook.md#обновление).

Это установка исполняемого файла. Средства развёртывания контракта и полный
кандидат для них подготавливаются по [инструкции развёртывания](../deployment/README.md).

## Профиль общего сервера

Установщик добавляет
`/etc/systemd/system/guard-daemon.service.d/20-shared-host.conf`:

- `Restart=on-failure`, пауза 30 секунд; лимит количества запусков отключён,
  поэтому длительный сетевой сбой не исчерпывает попытки;
- `MemoryHigh=256M`, `MemoryMax=384M`, `MemorySwapMax=0`;
- `CPUQuota=50%` — половина одного CPU, а не половина всех ядер;
- пониженные веса CPU и дискового ввода-вывода;
- до 128 задач, включая потоки процесса.

Это начальные ограничения для небольшого общего VPS, а не результат измерения
потребления демона. Память сверх `MemoryHigh` подвергается освобождению ядром;
если удержать расход ниже `MemoryMax` не удаётся, процесс может быть завершён
внутри своей cgroup и перезапущен. После настройки одной сети проверьте фактический
расход и частоту перезапусков.

Профиль дополняет базовый unit, в котором автоматический перезапуск выключен.
Для `v0.0.1` ошибки конфигурации, аттестации и состояния имеют тот же код `1`,
что и остальные ошибки: они тоже повторяются каждые 30 секунд. При постоянной
ошибке выполните `systemctl stop guard-daemon` и исправьте причину. Команда
`stop` останавливает и автоматические повторы. Проверки самого демона сохраняются
при каждой попытке запуска. Код HTTP `503` не вызывает перезапуск.

## Конфигурация и короткая проверка

Следуйте [описанию конфигурации](../configuration.md). Нужны адреса ролей,
RPC и манифест контракта для выбранной сети. При первом запуске задайте
`DRY_RUN=true`, оставьте оба файла credentials пустыми и не задавайте RPC отправки.
`STATE_DIRECTORY` задаётся установленным пакетом, а не операторским файлом.

После заполнения конфигурации:

```bash
set -euo pipefail
sudo systemctl start guard-daemon.service
sudo bash /usr/lib/guard-daemon/check-systemd-health.sh 200 healthy_idle
sudo systemctl show guard-daemon.service -p MemoryCurrent -p MemoryPeak -p NRestarts
```

Короткая проверка восстановления на dry-run:

1. Завершить только основной процесс guard-daemon через
   `systemctl kill --signal=SIGKILL --kill-whom=main guard-daemon.service`.
2. После 30 секунд убедиться в новом PID, увеличении `NRestarts` и ответе
   `healthy_idle` через скрипт проверки выше.
3. После успешной проверки включить автозапуск:
   `systemctl enable guard-daemon.service`.
4. Перезагрузку общего сервера проверять в согласованное окно обслуживания.
   После неё проверить активность службы и тот же ответ диагностики.

Логи доступны через `journalctl -u guard-daemon.service`. Конфигурацию сайта,
его процессы и сетевые порты установщик не изменяет. Диагностика guard-daemon
использует локальный Unix-сокет.
