# Быстрая обработка поступлений

Для реакции на новый блок вместо ожидания финализации задайте
`NETWORK_CONFIRMATION_MODE_<N>=latest`. Значение по умолчанию — `finalized`.
Для Base сочетание настроек рабочего режима выглядит так:

```dotenv
NETWORK_CONFIRMATION_MODE_BASE=latest
NETWORK_FEE_MODE_BASE=estimated
TOKEN_MODE_BASE=all
```

`TOKEN_MODE_BASE=all` нужен именно для неизвестных ERC-20. `known-only` и
`allowlist` сохраняют свои фильтры. Адреса ролей, RPC, контрактный манифест,
правила известных токенов и бюджеты задаются по общему справочнику.

## Когда появляется работа

Событие WebSocket будит ранний сканер. Два независимых RPC должны согласовать
свежий включённый блок и его логи по хешу. Находящийся только в mempool перевод
или неподтверждённый ответ одного провайдера не запускает платную операцию.
Периодический опрос работает и при недоступности WebSocket.

Ранний сканер проходит ограниченное окно `WATCH_LOOKBACK_BLOCKS`, начиная с
новейшего блока, и сохраняет отдельные подсказки о токенах в постоянной очереди.
Названия и decimals токенов не запрашиваются на критическом пути. Повторный
просмотр того же события, включая переподключение, сохраняет его ID.
Ранние задания dry-run имеют отдельные ID: проверочная обработка не поглощает
соответствующее задание рабочего режима.

Обычный финализированный сканер работает параллельно и продолжает вести
контрольные точки и восстанавливать пропуски. Ранние подсказки не становятся
членами финализированного блока и не мешают его обработке при смене ветки.
Исторический поток подтверждает события и пополняет реестр обнаруженных токенов,
не запуская заново сетевую подготовку для каждой записи. Существующие незавершённые
операции при смене режима продолжают согласовываться. Балансы известных и
обнаруженных активов дополнительно проверяются периодически; это также покрывает
поступления, пропущенные за пределами раннего окна после долгого отключения.
Окончательное подтверждение поступления не является предварительным условием
отправки: решение основывается на заново прочитанном согласованном балансе и
симуляции. Если после reorg баланса нет, перевод не отправляется.

## Путь до отправки

Подготовка одной попытки выполняется сетевыми фазами:

1. Параллельно: выбор свежего согласованного блока, чтение исходных данных
   комиссии, nonce sponsor и проверка незавершённых операций.
2. На одном хеше блока параллельно читаются балансы source/destination/sponsor
   и, для Base, L1/operator fee. Данные разных провайдеров должны совпасть.
3. Применяются лимиты и резервируется стоимость. Затем nonce source читается
   один раз непосредственно перед подписью EIP-7702 авторизации.
4. Параллельно выполняются кворумная симуляция, оценка газа и повторная проверка
   канонического хеша снимка. После них подписывается транзакция sponsor,
   сохраняются её точные байты и nonce, затем выполняется отправка.

Снимок живёт только в одной попытке и не переиспользуется после рестарта.
Если подготовка заняла более пяти секунд, новая подпись sponsor не создаётся;
запрос возвращается к подготовке с обычным ограничением повторов. Проверки
доступной суммы учитывают актуальные резервы ledger, даже когда используют
сохранённый в рамках попытки баланс. Неизменные привязки к хешу блока позволяют
не перечитывать один и тот же заголовок перед каждым balanceOf или eth_call.

Наличие текущей делегации не вызывает автоперевод ERC-20: платная транзакция
по-прежнему содержит собственную авторизацию и `sweepAll`. Для подготовленного
клейма используется `executeAndSweep` с тем же быстрым способом подготовки.

## После принятой отправки

Подтверждённая RPC отправка освобождает очередь и mutex подписания. Сохранённый
координатор продолжает отслеживать транзакцию в фоне. Успех операции и точный
расход фиксируются только по финализированной квитанции; до этого удерживается
полный резерв.

На один актив допускается одна незавершённая операция. Другой актив может
обрабатываться после того, как оба RPC подтвердят включение транзакции с
наибольшим выделенным nonce sponsor. Всего допускается до 16 незавершённых
операций сети. Повторное поступление того же токена может ждать финализации
предыдущей операции — это ограничение текущего быстрого режима.

Если принятая транзакция не включилась или пропала после reorg, по таймауту
квитанции повторно отправляются только те же сохранённые байты. Истёкший срок
клейма или согласования запрещает новые отправки, но не прекращает поиск
финализированной квитанции.
Для Base перед повторной отправкой заново проверяется оценка дополнительных
комиссий; устаревший снимок первой попытки для этого не используется.

При смене ветки снимок балансов может перестать быть каноническим. Если сама
транзакция затем финализировалась, её комиссия всё равно списывается полностью,
но по утраченному снимку не объявляется успешное спасение активов.
Режим исходного снимка сохраняется в записи операции: последующее изменение
настройки не превращает ранний снимок в финализированный.

Режим уменьшает задержку до первой отправки, сохраняя риск платной попытки на
нефинализированном состоянии. Он не гарантирует победу в гонке с владельцем
скомпрометированного ключа. Аттестация RescuerV2 при запуске остаётся
финализированной. Новые записи быстрых кандидатов не читаются `v0.0.1`.
