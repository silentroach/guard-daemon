НАЗНАЧЕНИЕ
───────────────────────────────────────────────────────────────────
Высокопроизводительный Go-демон для автоматического спасения токенов
со скомпрометированного кошелька (EOA) с использованием **EIP-7702**.

В безопасном режиме known-only мониторит только известные ERC-20.
Режим allowlist ограничивает заданные адреса, а неизвестные токены
доступны только после явного TOKEN_MODE_<N>=all.

**Главное:** одна транзакция = делегация + sweep. Никакого окна
для перехвата ботом.


ПРОБЛЕМА И РЕШЕНИЕ
───────────────────────────────────────────────────────────────────
Проблема (традиционный подход):
  tx1: сделать клейм токена
  tx2: переправить на безопасный адрес
  ↑ Между tx1 и tx2 (6-12 сек) бот мошенника перехватывает токены.

Решение (EIP-7702):
  Одна атомарная транзакция:
    1. SetCode авторизация (делегирование на RescuerV2)
    2. Вызов sweepAll([адрес_токена])
    
  ↑ Всё в одном блоке. Нет окна для атаки.


БЫСТРЫЙ СТАРТ
───────────────────────────────────────────────────────────────────
1. Установи Go 1.22+
   https://golang.org/dl

2. Скачай или склонируй:
   git clone https://github.com/Serge693/guard-daemon.git
   cd guard-daemon

3. Собери:
   go mod download
   go build -mod=readonly -o guard-daemon.exe ./cmd/guard-daemon
   (Linux/macOS: go build -mod=readonly -o guard-daemon ./cmd/guard-daemon)

4. Настрой .env:
   cp .env.example .env
   
   Оставь DRY_RUN=true и задай публичные роли, ENABLED_NETWORKS,
   два независимых RPC чтения и trusted manifest по
   docs/configuration.md. Приватные ключи в dry run не требуются.

5. Запусти:
   ./guard-daemon.exe

В dry run сообщения rescue_operation_confirmed быть не должно: этот режим
не подписывает и не отправляет транзакции.


НАСТРОЙКА .env
───────────────────────────────────────────────────────────────────
Авторитетный список полей, defaults и режимов:
  docs/configuration.md

Кратко:
  DRY_RUN=true включён по умолчанию.
  SOURCE_ADDRESS, SPONSOR_ADDRESS и DESTINATION_ADDRESS обязательны,
  ненулевые и попарно различные.
  ENABLED_NETWORKS явно перечисляет только нужные сети.
  Для каждой сети обязательны RESCUER_MANIFEST_<N>, два независимых
  RPC_READ_<1|2>_HTTP_<N>/WS_<N> и разные trust domain.
  TOKEN_MODE_<N>=known-only является безопасным default.
  SOURCE_PRIVATE_KEY и SPONSOR_PRIVATE_KEY читаются только из окружения
  live-процесса и не загружаются из .env.

Старые RESCUER_*, RPC_URL_*, RESCUE_TOKENS, TOKENS_TO_SWEEP,
CLAIM_* и SPONSOR_MIN_BALANCE не поддерживаются.

Дополнительные сети не входят в совместимый список internal/config.
Их включение требует отдельной проверки EIP-7702, настройки Rescuer
и изменения конфигурации.

Для каждой сети требуется:
  - trusted RESCUER_MANIFEST_<N>
  - два независимых RPC чтения
  - отдельный broadcast RPC только в live mode

Live startup загружает все manifests, затем требует согласия обоих RPC по
общему finalized block, deployment transaction/receipt, runtime и immutable
ролям. Signers создаются только после успешной аттестации всех сетей.


КАК РАБОТАЕТ ДЕМОН
───────────────────────────────────────────────────────────────────
Основной цикл (на каждой сети):

  1. Слушает Transfer-события на блокчейне
     (адрес получателя = SOURCE_ADDRESS)

  2. При получении события:
     a. Проверяет token policy; unknown metadata запрашивает только при
        явном режиме all или для неизвестного адреса allowlist
     b. Проверяет баланс (> 0?)
     c. Запускает renewAndSweep() — атомарная транзакция

  3. renewAndSweep() (одна EIP-7702 транзакция):
     a. SOURCE подписывает SetCode авторизацию (локально, без газа)
     b. SPONSOR собирает tx с авторизацией + вызовом sweepAll()
     c. Отправляет в сеть

  4. RescuerV2 (контракт):
     a. Получает вызов с делегированным SOURCE EOA
     b. Проверяет _verifyDelegation() (делегация на нас?)
     c. Если ОК: переводит весь баланс токена на DESTINATION
     d. Если FAIL: откатывается (токены остаются в безопасности)

  5. Результат:
     ✓ Если успех → токены на DESTINATION
     ✗ Если ошибка → будет повторная попытка автоматически (см. ниже)

Периодическая проверка (каждые ~12 секунд в WebSocket-режиме):
  - Проверяет активна ли делегация
  - Если нарушена: восстанавливает через renewDelegation()
  - Свипирует малое количество нативного газа если много
  - Перепроверяет баланс каждого известного токена на источнике и
    ПОВТОРЯЕТ sweep, если баланс всё ещё положительный — это
    покрывает случай, когда предыдущий renewAndSweep() откатился
    (например, из-за гонки за nonce или временной ошибки RPC), а
    токены остались на месте. Без этого токены, пережившие неудачную
    попытку, просто лежали бы до следующего внешнего Transfer-события,
    которое может никогда не прийти.

УСТРАНЕНИЕ ПРОБЛЕМ
───────────────────────────────────────────────────────────────────

"Delegation dropped — renewing..."
  → Нормально, если бот тоже пытается своп.
  → Демон будет восстанавливать делегацию автоматически.

"ERR renewAndSweep reverted" — как реально диагностировать
  → Не гадай по расходу газа — просимулируй точный вызов через
    read-only eth_call (без приватного ключа, без реальной
    транзакции) и прочитай selector ошибки:

      client.CallContract(ctx, ethereum.CallMsg{
          From: sponsorAddr, To: &srcAddr, Data: sweepAllCalldata,
      }, nil)

    Если ошибка реализует интерфейс rpc.DataError — вызови
    .ErrorData(), чтобы получить сырые байты revert. Первые 4 байта
    — selector кастомной ошибки; сравни с error-объявлениями в
    своём контракте (DelegationNotActive(), TransferFailed()),
    чтобы точно понять что сработало.

  → Возможные причины (примерно по частоте):
    1. DelegationNotActive() срабатывает, хотя делегация выглядит
       правильной ончейн — см. отдельный раздел ниже, это был
       реальный баг в контракте, а не проблема делегации
    2. Недостаточно газа у спонсора на конкретной сети
    3. Чужая SetCodeAuthorization попала в тот же блок с меньшим
       nonce (настоящая гонка условий — редко, но возможно)
    4. Необычная логика в контракте токена (blacklist, pause)

⚠️ DelegationNotActive() при явно правильной делегации
───────────────────────────────────────────────────────────────────
Это больно ударило во время разработки, стоит задокументировать
точно — легко повторить эту же ошибку, если снова трогать
_verifyDelegation().

Ловушка: во время исполнения кода через EIP-7702 делегацию,
address(this) внутри контракта-делегата НЕ указывает на адрес
самого этого контракта — он указывает на ДЕЛЕГИРУЮЩИЙ EOA
(скомпрометированный EOA). Потому что
байткод делегата исполняется "от лица" EOA: address(this),
msg.sender во внешнем фрейме, storage и balance — всё это
привязано к EOA, а не к контракту, чей код одолжен.

Две сломанные версии, которые реально были задеплоены по очереди:

  1. Проверка msg.sender — это кошелёк-спонсор (тот, кто отправил
     транзакцию), обычный EOA без делегации. Ревертит всегда.

  2. Проверка address(this) — кажется логичным ("проверь свой
     собственный designator"), но address(this) в момент вызова
     равен ДЕЛЕГИРУЮЩЕМУ адресу, а не этому контракту. Проверка
     превращается в "равен ли адрес получателя делегации адресу
     самого делегирующего" — что никогда не может быть истиной,
     потому что designator всегда указывает на реальный адрес
     RescuerV2, а не на сам EOA. Ревертит всегда, без явного
     сигнала, что баг именно в проверке, а не в делегации.

Исправление: сохранить собственный адрес контракта в immutable,
установленный в конструкторе — единственном месте, где
address(this) гарантированно означает адрес именно этого
контракта, потому что конструктор всегда исполняется в
собственном контексте деплоя, никогда через делегацию:

  address public immutable self;

  constructor(address _destination) {
      destination = _destination;
      self = address(this);   // корректно сохранено здесь, при деплое
  }

  function _verifyDelegation() internal view {
      bytes memory code = address(this).code;  // верно: код ДЕЛЕГИРУЮЩЕГО
      // ... парсинг 0xef0100 + 20-байтный адрес ...
      if (delegatedTo != self) revert DelegationNotActive();  // сравнение с immutable
  }

Если будешь ещё раз редеплоить или менять контракт — держи в
голове: читать designator нужно из address(this) (делегирующий,
в момент вызова), а СРАВНИВАТЬ его нужно с self (сам контракт,
зафиксированный при деплое) — никогда не сравнивай address(this)
с самим собой, это всегда даст неверный результат.

"RPC chain ID mismatch"
  → RPC-эндпоинт указывает на другую сеть.
  → Проверь оба RPC_READ_<1|2>_HTTP_<N> и RPC_READ_<1|2>_WS_<N>.

"аттестация deployment заблокирована"
  → Trusted RESCUER_MANIFEST_<N>, runtime, finalized block, sponsor
    или destination не согласованы двумя независимыми RPC.
  → Проверь manifest и RPC по docs/configuration.md.
  → Не обходи эту проверку — она специально не даёт средствам
    молча уйти не туда.

"некорректный EVM-адрес" (или похожее при старте)
  → Публичная роль или токен в allowlist не является корректным адресом.
  → Скорее всего опечатка. Демон намеренно падает здесь громко —
    иначе опечатка могла бы тихо превратиться в другой,
    валидно выглядящий, но неверный адрес.

"insufficient funds for gas"
  → Баланс спонсора очень низкий.
  → Добавь 0.01+ ETH и перезапусти.

"transaction type is not supported" (zkSync)
  → Секвенсер zkSync пока не принимает EIP-7702 Type-4 транзакции.
  → Это ограничение сети. Демон будет безобидно повторять попытки
    делегации, но своп на zkSync не заработает до появления
    поддержки на уровне сети.

"symbol() call failed"
  → Токен нестандартный или контракт невалиден.
  → Демон покажет адрес вместо символа, sweep продолжится.


БЕЗОПАСНОСТЬ
───────────────────────────────────────────────────────────────────

Что защищено на уровне кода (после аудита и правок):

  ✓ executeAndSweep() ограничен только спонсором (onlySponsor)
    — без этого кто угодно мог бы заставить делегированный EOA
    вызвать approve() или любую другую функцию на любом токене,
    в обход immutable destination
  ✓ Конструктор RescuerV2 теперь принимает ДВА аргумента:
    (destination, sponsor) — деплой с одним аргументом просто
    не пройдёт, это ожидаемое, безопасное поведение
  ✓ Проверка при старте: chainId у RPC совпадает с ожидаемым,
    и on-chain destination() контракта совпадает с .env —
    иначе демон откажется запускаться на этой сети
  ✓ Адреса из .env строго валидируются — опечатка (неверная
    длина, лишний символ) вызывает явную ошибку при старте,
    а не тихую подстановку другого адреса
  ✓ Лимит повторов (3 попытки) для зависшего/сломанного токена
    теперь действует централизованно внутри renewAndSweep() —
    не обходится ни через живые события, ни через periodicCheck
  ✓ Верхний предел газа применён ко ВСЕМ трём типам транзакций,
    оплачиваемых спонсором (sweep, обновление делегации, sweepEth),
    не только к sweep — иначе скачок сети мог привести к
    непредсказуемо дорогой транзакции
  ✓ Успешный receipt сам по себе не считается доказательством
    свипа — демон дополнительно проверяет реальный баланс,
    т.к. при проигранной nonce-гонке транзакция могла молча
    исполниться через чужую (атакующего) делегацию
  ✓ Permit flow в Go daemon отсутствует: ABI, адрес и fallback
    не загружаются. Production path использует только RescuerV2.
    Legacy contract и deployment artifacts удаляются отдельными
    задачами усиления контракта и воспроизводимого деплоя.

Рекомендации:

  ⚠ Никогда не коммитьте .env в GitHub
  ⚠ Храните приватные ключи в безопасности
  ⚠ Используйте аппаратный кошелёк для спонсора, если возможно
  ⚠ Мониторьте логи на необычную активность
  ⚠ Планируйте миграцию на новый кошелёк со свежим ключом
  ⚠ После любого редеплоя RescuerV2 отдельно проверяйте runtime
    и immutable параметры. Общий положительный вывод legacy
    deployment script не доказывает безопасный деплой.

  ✓ После успешного rescue не используйте старый адрес для нового value
  ✓ Поделитесь опытом в сообществе (помогает другим в похожей ситуации)


ЛОКАЛЬНАЯ ПРОВЕРКА DEPLOYMENT TOOLING
───────────────────────────────────────────────────────────────────
Поддерживается только воспроизводимая локальная процедура:

  docs/deployment/local-verification.md

Она проверяет canonical artifact, default no-broadcast plan, локальный Anvil,
runtime, immutable getters и manifest. Старые multi-network/Permit scripts,
ручная компиляция Remix и прямое копирование адреса в .env удалены из
поддерживаемого процесса.

Без явного --broadcast CLI не обращается к RPC, не читает приватный ключ,
не подписывает и не отправляет транзакцию. Production/mainnet activation
описывается только после отдельной эксплуатационной проверки Task 10.


ПРОВЕРКА ДО ПРОДАКШЕНА
───────────────────────────────────────────────────────────────────
DRY_RUN=true не читает private keys, не создаёт production signer/broadcaster,
не подписывает и не отправляет транзакции. После подключения он выполняет
только read-only планирование и EstimateGas.

DRY_RUN=false требует private keys, отдельный broadcast RPC и успешную
quorum-аттестацию до создания signers. До завершения Tasks 06-11 этот режим
не является разрешением на production-запуск.
